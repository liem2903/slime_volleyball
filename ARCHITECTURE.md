# Slime Volleyball — Architecture Reference

> Self-contained reference doc for the `slime_volleyball` codebase. Generated by reading the backend (routes, middleware, controllers, business logic, data/repository layer, DB schema), the integration test suite, and a lighter pass over the frontend. Intended to be loaded as context in a session that has no prior history with this repo.

## 1. What this app is

A tool for organizing pickup volleyball sessions: a **host** creates a session (date/time/court/cost/capacity), shares a join link, players **join** (and get waitlisted once capacity is hit), the host can **lock** the session to split the cost and demand payment, players **pay**, and the session **auto-completes** once everyone has paid. There are no user accounts — auth is entirely via opaque bearer-style tokens embedded in shareable URLs (an "admin token" for the host, a "user token" per player).

## 2. Tech stack

- **Backend**: Node/Express 4 + TypeScript, raw `pg` (node-postgres) driver — **no ORM**, hand-written SQL only. Zod for request-body validation. Jest + `ts-jest` + Supertest for integration tests against a **real** Postgres instance (via `docker-compose`), not mocks.
- **Frontend**: React + `react-router-dom` + `axios`, Vite dev server (default `localhost:5173`).
- **DB**: Postgres 16 (`docker-compose.yml`, db `vball`). Single flat SQL migration file, no migration framework/history table.

## 3. Layering

```
HTTP request
  → routes/*.ts            (Express Router definitions, path + method + middleware wiring)
  → middleware              (validate() for Zod schemas, check_is_admin for auth)
  → controllers/*.ts        (thin: parse req, call one business fn, shape JSON response)
  → business/*Business.ts   (thin pass-through + token/link generation; almost no invariants)
  → data/*Repository.ts     (real business rules + SQL + transactions/row-locking live here)
  → setup/data.ts (pg.Pool) → Postgres
  ← error_handler middleware (mounted last) turns thrown errors into HTTP responses
```

**Key architectural fact**: unlike a typical layered app, the *business* layer here does almost nothing — it's mostly one-line delegates. The actual invariants (state machine rules, capacity math, locking) all live in the **repository** layer, mixed in with the raw SQL. Read the repositories, not the business files, to understand what the app actually enforces.

## 4. Domain model (`migrations/001_initial_schema.sql`)

### Enums
- `session_state`: `'unlocked' | 'locked' | 'completed' | 'cancelled'` (default `'unlocked'`)
- `attendance_state`: `'waitlist' | 'interested' | 'payment_pending' | 'confirmed' | 'cancelled' | 'payment_cancelled'` (default `'interested'`)

### `sessions` table
| column | type | notes |
|---|---|---|
| id | TEXT PK | a `crypto.randomUUID()` string, not a native UUID type |
| host_name, host_email | VARCHAR(255) | |
| created_at | TIMESTAMPTZ | default now() |
| admin_token_hash | VARCHAR(255) | SHA-256 of the host's opaque admin token — **this is the host's credential**; the raw token is never stored, only ever returned once in the create-session response |
| date | DATE | |
| time_start, time_end | TIMESTAMPTZ | |
| cost_cents | INTEGER | total session cost |
| capacity | INTEGER | max "counted" attendees (interested/confirmed/payment_pending) |
| court_name | TEXT | nullable |
| player_count | INTEGER | **manually maintained counter**, not a computed/aggregate column — every repository function that adds/removes a counted attendee must increment/decrement this itself |
| price_per_player | INTEGER | nullable; computed only when the session is locked |
| state | session_state | default `'unlocked'` |

### `attendances` table
| column | type | notes |
|---|---|---|
| id | TEXT PK | |
| name, email | VARCHAR(255) | |
| user_token_hash | VARCHAR(255) | SHA-256 of the player's opaque personal token — **this is the player's credential** for self-service actions (leaving, looking up their own id) |
| state | attendance_state | default `'interested'` |
| session_id | TEXT | FK → `sessions(id)` |
| joined_at | TIMESTAMPTZ | default now(); used to order waitlist promotion FIFO (`ORDER BY joined_at ASC`) |
| — | `UNIQUE(email, session_id)` | one signup per email per session; violation → Postgres error `23505` → mapped to HTTP 409 `ConflictError` ("ALREADY BOOKED") via `backend/src/errorHandling/DataBaseErrorParser.ts` |

Relationship: 1 `sessions` row → many `attendances` rows.

**Important quirk**: if the host opts to count themself as a player (`host_is_player: true` at creation), they are represented **only** by `sessions.player_count` starting at `1` — there is **no `attendances` row for the host**. The host never appears in `getPlayers`/`getWaitlist` results and has no pay/confirm flow of their own.

## 5. Bootstrapping (`backend/src/setup/`)

- **`data.ts`**: creates one shared `pg.Pool` from `DATABASE_URL` (loaded via `dotenv`), `connectionTimeoutMillis: 5000`, `statement_timeout: 10000`. Imported everywhere as `pool`.
- **`app.ts`**: builds the Express app —
  1. `express.json()`
  2. `/api/session` → `sessionRouter`
  3. `/api/players` → `playerRouter`
  4. `/api/admin/:sessionId/:adminId` → **`check_is_admin` middleware, then** `adminRouter`
  5. `error_handler` (mounted last, catches everything)
- **`index.ts`**: `app.listen(PORT || 3001)`.
- `backend/src/routes/index.ts` exists (a generic router with just `/health`) but is **never mounted** — dead code, ignore it.

### Transaction / locking pattern
Any operation that reads then mutates state in a way that must be atomic under concurrency:
1. Checks out a **dedicated client** via `pool.connect()` (not the shared `pool.query`).
2. Manually issues `BEGIN` … `COMMIT` / `ROLLBACK` in `try/catch/finally`, always `client.release()`-ing in `finally`.
3. Uses `SELECT ... FOR UPDATE` to pessimistically row-lock the `sessions` row (and sometimes `attendances` rows) it's about to read-then-mutate, so concurrent requests against the same session serialize instead of racing on `player_count`/`capacity`/`state`.

Simple, single-statement reads/writes (e.g. `getSessionData`, `getPlayerRepository`) just use `pool.query(...)` directly with implicit auto-commit — no dedicated client, no lock.

This locking is what the race-condition integration tests are specifically designed to validate (see §8).

## 7. Middleware (`backend/src/middleware/sessionMiddleware.ts`)

- **`validate(schema: z.ZodType)`** — factory. Runs `schema.safeParse(req.body)`. On failure: `400 {errors: z.prettifyError(...)}`, request stops here. On success: replaces `req.body` with the parsed/coerced data, calls `next()`.

- **`check_is_admin(req, res, next)`** — the host-auth gate, applied to the whole `/api/admin/:sessionId/:adminId` mount before `adminRouter` runs:
  1. Reads `sessionId`, `adminId` from `req.params`.
  2. SHA-256-hashes `adminId`.
  3. Calls `checkIsAdmin(sessionId, hash)` (in `sessionRepository.ts`): `SELECT * FROM sessions WHERE id = $1 AND admin_token_hash = $2`, returns `true` iff exactly one row matches.
  4. If not admin: calls `next(new UnauthorisedRequest())`.
  5. **Regardless**, falls through to `req.params = {sessionId}` (strips `adminId` before handing off to `adminRouter`) and calls `next()` again unconditionally.

  > ⚠️ **Bug**: step 4 is missing a `return`. On the unauthorized path, `next()` gets called **twice** — once with an error (routed to `error_handler`, which sends 401) and once without (which continues into `adminRouter`'s handler stack). This is fragile double-dispatch; it happens to not break the current integration tests (because the downstream repository calls also independently reject/no-op), but it's a real latent bug, not by-design behavior.

- **`error_handler(err, req, res, next)`** — mounted last in `app.ts`, catches everything thrown/passed-to-`next` upstream:
  - Logs `err.message`.
  - If `err instanceof AppError` (see below): `res.status(err.statusCode).json({message: err.message})`.
  - If `err instanceof ZodError`: `res.status(400).json({message: "Zod error " + err.message})`.
  - **Otherwise: `return err`** — does *not* call `res.send`/`res.json`. For any error type outside `AppError`/`ZodError`, no HTTP response is ever sent and the request hangs. This is a real gap, not intentional behavior (e.g. it's what makes sending an invalid enum value to `lockSession`'s `state` field hang instead of erroring cleanly, since that surfaces as a raw Postgres enum error).

### Error types (`backend/src/errorHandling/error.ts`)
`AppError` base class with `statusCode` + `errorCode`; subclasses: `NotFoundError` (404), `InvalidParametersError` (400, "Parameters don't exist"), `ConflictError` (409), `BadRequestError` (400, custom message+code), `UnauthorisedRequest` (401).

### DB error mapping (`backend/src/errorHandling/DataBaseErrorParser.ts`)
`ErrorParse(err)` — Postgres error code `23505` (unique violation) → thrown as `ConflictError`; everything else rethrown unchanged. Every repository's `catch` block funnels `DatabaseError` instances through this.

## 8. Feature walkthroughs

### 8.1 Create session
`POST /api/session/create` → `validate(SessionSchema)` → `sessionController.createSession` → `sessionBusiness.createSessionBusiness` → `sessionRepository.createSessionData`.

- Business layer generates `session_id` and `opaque_token` via `crypto.randomUUID()`.
- Builds ISO timestamps by combining `date` + `time_start`/`time_end`.
- Builds two shareable URLs: `join_link = http://localhost:5173/session/{id}` and `host_link = http://localhost:5173/session/{id}/{opaque_token}` — **hardcoded to localhost:5173, not environment-driven**.
- SHA-256-hashes the opaque token → `admin_token_hash` (the raw token is only ever in the response, never persisted).
- Converts `price` (dollars, presumably from the frontend form) to `cost_cents` via `Math.round(price * 100)`.
- Sets initial `player_count = host_is_player ? 1 : 0` (no `attendances` row for the host — see §4).
- `INSERT INTO sessions (...)`. Response: `{host_link, join_link, session_id}`.

### 8.2 Get session
`GET /api/session/:sessionId` → `getSession` → `getSessionBusiness` → `getSessionData`: `SELECT * FROM sessions WHERE id = $1`; throws `NotFoundError` (404) if missing.

### 8.3 Join a session (`createPlayerRepository`, transactional)
`POST /api/players/create` → `validate(PlayerSchema)` → `createPlayer` → `createPlayerBusiness` (generates `player_id`, `user_token`, builds `user_link = http://localhost:5173/player/{session_id}/{user_token}`, hashes token) → `createPlayerRepository`:
1. `SELECT state FROM sessions WHERE id=$1 FOR UPDATE` — row-locks the session, serializing concurrent joins.
2. If session is `'locked'`: new attendee goes straight to `'waitlist'` (locked sessions never accept new interested players).
3. Else: attempts `UPDATE sessions SET player_count = player_count + 1 WHERE id=$1 AND player_count < capacity` — an atomic "reserve a spot" operation. If it affected a row → attendee is `'interested'`; otherwise (session was already full) → `'waitlist'`.
4. `INSERT INTO attendances` with the resulting state. `UNIQUE(email, session_id)` prevents double-signup (→ 409).
5. Returns the resulting state string, which flows back up into the API response (`PlayerResponse.user_state`) so the frontend knows whether the new player landed on the roster or the waitlist.

This `FOR UPDATE` + conditional `UPDATE ... WHERE player_count < capacity` pair is what makes the "20 concurrent joins against capacity 6" integration test deterministic.

### 8.4 Get players / waitlist / id-from-token
- `getPlayerRepository(session_id)`: `SELECT id, name WHERE session_id=$1 AND (state='interested' OR state='confirmed')` — the "roster" view.
- `getWaitlistRepository(session_id)`: `SELECT id, name WHERE session_id=$1 AND state='waitlist'`.
- `getIdFromTokenRepository(encryptedToken)`: `SELECT id FROM attendances WHERE user_token_hash=$1`. **Bug**: `playerBusiness.getIdFromTokenBusiness` calls this but doesn't `return` the result, so the controller always receives `undefined`. Also unreachable anyway per the routing bug in §6.

### 8.5 Player self-drop-out (`deletePlayerRepository`, transactional)
`DELETE /api/players/delete/:sessionId/:userToken` → controller hashes `userToken` → `deletePlayerBusiness` → `deletePlayerRepository`:
1. `SELECT player_count, capacity, state FROM sessions WHERE id=$1 FOR UPDATE`.
2. `DELETE FROM attendances WHERE user_token_hash=$1` (scoped by token only, not further by `sessionId` — the token is globally unique per player so this is safe in practice).
3. If `player_count == capacity` (session was full): promote the earliest-joined waitlisted attendee (`ORDER BY joined_at ASC LIMIT 1`) — to `'payment_pending'` if the session is `'locked'`, else `'interested'`. If nobody's waitlisted, decrement `player_count`.
4. Else (session wasn't full): unconditionally decrement `player_count`.

**Behavioral note**: promotion/decrement is decided by comparing `player_count` to `capacity` (i.e. "was the session full"), **not** by checking whether the specific player who left actually held one of the counted slots. This is intentional/tested behavior for the flows the test suite covers, but is worth understanding precisely rather than assuming per-player-state-driven logic.

### 8.6 Admin: lock session (`lockSessionRepository`, transactional)
`PATCH /api/admin/:sessionId/:adminId/lockSession` (body `{state}`, validated by `ChangeStateSchema`) → `check_is_admin` → `lockSession` → `lockSessionBusiness` → `lockSessionRepository(state, sessionId)`:
1. Rejects if the session is **already** in the requested state → `BadRequestError` ("REDUNDANT CHANGE", 400).
2. `SELECT cost_cents, player_count FROM sessions WHERE id=$1 FOR UPDATE`.
3. **Invariant: `player_count >= 2`** required, else `BadRequestError` ("NOT ENOUGH PLAYERS", 400).
4. `UPDATE sessions SET state = $1`.
5. Computes `price_per_player = ceil(cost_cents / player_count)` and persists it — this is when the split price is finalized.
6. Bulk-converts every `'interested'` attendance for the session → `'payment_pending'` — this is what makes locking "start the payment collection" for everyone currently on the roster.

Note: this function is generic over `state` (not hardcoded to `'locked'`) and always runs the price-calc + payment-pending conversion regardless of which state string is passed — in practice only reachable with a non-`'locked'` value if a client sends something else through the schema, since the route/UI only ever sends `'locked'`.

### 8.7 Admin: kick player (`kickPlayerRepository`, transactional)
`DELETE /api/admin/:sessionId/:adminId/:playerId/deletePlayer`:
1. Row-locks `sessions`; validates both the session and the target `attendances` row exist → `InvalidParametersError` ("Parameters don't exist", 400) otherwise.
2. **Invariant: session must be `'unlocked'`** → `BadRequestError` ("WRONG STATE", 400) otherwise.
3. If session was at capacity: promote the earliest waitlisted player to `'interested'` if one exists, else decrement `player_count`.
4. Else (not at capacity): if the kicked player was specifically `'interested'`, decrement `player_count` (kicking a waitlisted player never touches the counter, since waitlisted players were never counted).
5. `DELETE FROM attendances WHERE id=$1`.

### 8.8 Admin: swap waitlist ⇄ interested (`swapStatesRepository`, transactional)
`PATCH /api/admin/:sessionId/:adminId/:waitlistId/:interestedId/swapStates`:
1. Row-locks both attendance rows (`FOR UPDATE`); validates `waitlistId`'s row is currently `'waitlist'` and `interestedId`'s row is currently `'interested'` → `InvalidParametersError` otherwise.
2. **Invariant: session must be `'unlocked'`** → `BadRequestError` ("Wrong State", 400) otherwise.
3. Flips the two states. `player_count` is untouched (net count unchanged by a swap).

> ⚠️ Unlike `kickPlayerRepository`, this function does **not** validate that the two IDs actually exist as rows before querying their `.state` — if a bogus ID is passed, the code will throw on `undefined.state` rather than a clean `InvalidParametersError`. No test currently covers a nonexistent-ID swap.

### 8.9 Admin: confirm payment (`confirmPlayerRepository`, transactional)
`PATCH /api/admin/:sessionId/:adminId/:playerId/confirm`:
1. Row-locks the session. **Invariant: session must be `'locked'`** → `BadRequestError` ("Player is not in locked session", 400).
2. Looks up the attendance row scoped to `(playerId, sessionId)` → `NotFoundError` (404) if missing.
3. **Invariant: attendance must be `'payment_pending'`** → same `BadRequestError` reused.
4. Sets the attendance to `'confirmed'`.
5. **Auto-completion**: checks whether any `'payment_pending'` attendances remain for the session — if none, flips `sessions.state` → `'completed'`. This is how a session transitions `locked → completed`: implicitly, as a side effect of the *last* pending payment being confirmed — there's no separate explicit "complete session" admin action.

The session-row lock (`FOR UPDATE`) + transaction is what makes concurrent confirms deterministic (both serialize; only the confirm that observes zero remaining `payment_pending` flips the session to completed).

### 8.10 Admin: unlock session — **not actually implemented**
`PATCH /api/admin/:sessionId/:adminId/unlockSession`:
- `unlockSessionRepository(state, sessionId)` is an **empty stub**: `try { } catch { }` — no SQL at all, does nothing, never throws.
- `unlockSessionBusiness` just delegates to it.
- `adminController.unlockSession` **never calls `res.json(...)`/`res.status(...)` on success** — so a request to this endpoint currently **hangs** (no response ever sent) rather than completing.
- The integration test suite (`admin.test.ts`) documents the *intended* behavior in detail even though it's not implemented: should reset `sessions.state` → `'unlocked'` and `price_per_player` → `null`; should be blocked (400, no mutation) if any attendance is already `'confirmed'`; should 404 if the session doesn't exist.

This is the single largest functional gap in the admin flow.

## 9. Business layer summary

Every business function is a thin pass-through, with two exceptions that do real work:
- `sessionBusiness.createSessionBusiness` — token/id generation, link building, dollars→cents conversion, initial `player_count` seeding.
- `playerBusiness.createPlayerBusiness` — token/id generation, link building, delegates the actual join/waitlist decision to the repository.

All state-machine invariants (locking rules, capacity math, waitlist promotion, payment gating) live in the **repository** layer (§8), not here.

## 10. Tests (`backend/src/tests/`)

### Infrastructure
- **Framework**: Jest 30 + `ts-jest` (`backend/jest.config.js`, `testEnvironment: "node"`).
- **HTTP layer**: Supertest against the real Express `app` exported from `backend/src/setup/app.ts` — no manual server startup needed.
- **Database**: **real Postgres**, not mocked — the same `pool` (`setup/data.ts`) used by the app, pointed at `postgres://postgres:dev@localhost:5432/vball` (matches root `docker-compose.yml`, Postgres 16). A local Postgres via `docker compose up` must be running, with the schema applied via `backend/package.json`'s `db:migrate` script (which sources `.env` and pipes `migrations/001_initial_schema.sql` into `psql`).
- **Run**: `cd backend && npm test` (runs `jest`).
- **Known infra gap**: no `afterAll(() => pool.end())` / Jest global teardown anywhere — Jest may hang after a full run as the suite grows (noted in `tests_feedback.txt`).
- This is a genuine **integration** suite: it exercises controller → business → repository → real SQL, including the `FOR UPDATE` row-locking behavior, via real concurrent requests.

### `backend/src/tests/integration/helpers/session.testHelper.ts`
Shared fixtures (not itself a test file):
- `addSession` / `addAdminSession` — insert a session directly via SQL; `addAdminSession` generates a real token, hashes it, and returns both the raw token (used as the admin URL segment) and the session id.
- `findSession`, `deleteSession`, `getSessionState`, `getPricePerPlayer`, `getSessionPlayerCount`.
- `addInterestedPlayer`, `addWaitlistedPlayer`, `addPaymentPendingPlayer` — insert `attendances` rows directly in a given state (bypassing the API) to arrange preconditions fast.
- `deletePlayer`, `getPlayerCount`, `doesPlayerExist`, `getPlayerState`, `getPlayerId`, `getPlayersAndWaitlist`.
- `lockSession(id)` — directly sets a session to `'locked'` and computes `price_per_player`, bypassing the controller — a shortcut for "arrange an already-locked session" preconditions.
- `markPlayerPaid(playerId)` — directly sets an attendance to `'confirmed'`.

### `session.test.ts`
- `POST /api/session/create`: happy path (verifies `host_link`/`join_link`/`session_id` and that the DB row matches submitted fields, incl. cents conversion and date/time parsing); Zod rejects an invalid host email (400).
- `GET /api/session/:sessionId`: happy path.
- Empty placeholder `describe("Session marked as completed once all players have paid")` — no tests implemented there (that flow is actually covered in `admin.test.ts`'s confirm-payment tests instead).

### `player.test.ts`
- `GET /api/players/:sessionId` / `/waitlist/:sessionId`: happy path.
- `POST /api/players/create`:
  - Multiple happy-path joins → `'interested'`, capacity respected.
  - `host_is_player: false` case still counts the host in `player_count`.
  - **Race test**: 20 concurrent joins against capacity 6 → asserts exactly 5 land `'interested'` and 15 `'waitlist'` (1 slot pre-taken by the host) — validates the capacity-guard locking in §8.3.
  - Joining a **locked** session → straight to `'waitlist'`.
- `DELETE /api/players/delete/:sessionId/:userToken`:
  - No-waitlist case → count decrements to 0.
  - Waitlisted player gets promoted when an interested player leaves.
  - **Race test**: two concurrent deletes at capacity with a waitlisted player queued → asserts correct final promotion (validates `FOR UPDATE` locking in §8.5).
  - Leaving a **locked** session with a waitlist → promoted player lands in `'payment_pending'`.
  - Leaving a **locked** session with no waitlist → `price_per_player` correctly unaffected.

### `admin.test.ts`
Covers all admin routes under `/api/admin/:sessionId/:adminId/...`:
- **Lock session**: happy path (locks + promotes `'interested'`→`'payment_pending'`); rejects redundant state change (400); rejects unauthorized admin token (401, state unchanged); rejects invalid enum value (asserted 400, though per §7 this actually risks hanging in real usage due to the `error_handler` gap — flagged in `tests_feedback.txt`); verifies `price_per_player` rounding.
- **Kick player**: happy path promotes the earliest-queued waitlisted player; blocked when locked (400); no-waitlist decrement case (⚠️ per `tests_feedback.txt` this test doesn't actually exercise the pure-decrement branch as intended — a real gap in the *test*, not the app); nonexistent player → 400; unauthorized → 401 no mutation; **race test**: repeated concurrent double-kicks validating locking.
- **Swap states**: happy path; blocked when locked (400); unauthorized (401). No test for a nonexistent player ID (matches the repository gap noted in §8.8).
- **Unlock session**: happy path (resets state + price); blocked if anyone already `'confirmed'` (400); 404 for nonexistent session. **These tests describe intended behavior only — the feature itself is an unimplemented stub (§8.10)**, so treat this describe block as a spec, not proof the feature works.
- **Confirm payment**: happy path → `'confirmed'`; confirming outside a locked session → 400; session auto-transitions to `'completed'` once the last pending payment confirms; confirming a nonexistent player → 404; confirming a player not in `'payment_pending'` → 400; **race test**: 2 concurrent confirms in a 3-capacity session, looped 5x, asserting both end up `'confirmed'` and the session ends up `'completed'` exactly once.

### `tests_feedback.txt` (repo root)
A code-review-style note (not raw test output) that independently corroborates several of the bugs/gaps listed here (the `check_is_admin` missing `return`, the `error_handler` hang on invalid enum values, `swapStatesRepository`'s missing existence check, the mislabeled kick-with-no-waitlist test, missing pool teardown, and stray debug `console.log`s / boxed-`String` typing in the test helper) plus a suggested priority order for fixing app bugs vs. test hygiene vs. new coverage.

### Backend API calls, by page
- **HomePage**: `POST /api/session/create` → builds a local placeholder `Session` to display the host/join links.
- **SessionPage**: on mount `GET /api/session/:sessionId`, `GET /api/players/:sessionId`, `GET /api/players/waitlist/:sessionId`. Looks like unfinished wiring.
- **AdminPage**: on mount, the same three GETs. "Remove player" → `DELETE /api/admin/:sessionId/:adminId/:playerId/deletePlayer`. "Move to Payment" → `PATCH /api/admin/:sessionId/:adminId/lockSession` (`{state: 'locked'}`). **Does not yet call** `unlockSession`, `swapStates`, or `confirm` — those admin routes exist and are tested on the backend but have no UI entry point yet.
- **PlayerPage**: on mount the three GETs plus `GET /api/players/:userToken` (intended to resolve the URL token to `myPlayerId` — but see the route-collision bug in §6, this call is effectively broken against the real backend). "Leave Session" → `DELETE /api/players/delete/:sessionId/:userToken`. Shows "You owe: {price_per_player}" once locked.
- **Popup components** (`JoinInfoPopup`, `JoinSessionPopup`, `SwapToWaitlistPopup`) are pure controlled forms with client-side validation; they call an `onSubmit`/`onSelect` callback from the parent page rather than hitting the backend directly.

**Full API surface actually used by the frontend today**: `POST /api/session/create`, `GET /api/session/:sessionId`, `GET /api/players/:sessionId`, `GET /api/players/waitlist/:sessionId`, `GET /api/players/:userToken` (broken, see above), `POST /api/players/create`, `DELETE /api/players/delete/:sessionId/:userToken`, `DELETE /api/admin/:sessionId/:adminId/:playerId/deletePlayer`, `PATCH /api/admin/:sessionId/:adminId/lockSession`. Backend endpoints implemented + tested but **not yet wired into any UI**: `unlockSession` (also non-functional server-side, §8.10), `swapStates`, `confirm`.

## 12. Consolidated list of known bugs / gaps

For quick reference — all verified against source, not just inferred from tests:

1. **`unlockSession` is non-functional** — empty repository stub, controller never sends a response on success (hangs), route has no body validation. (§8.10)
2. **`check_is_admin` double-dispatches `next()`** on the unauthorized path (missing `return` after `next(new UnauthorisedRequest())`). (§7)
3. **`error_handler`'s fallback branch hangs the request** — for any error that isn't `AppError`/`ZodError` (e.g. a raw Postgres enum error from an invalid `state` value), it `return`s the error object instead of sending a response. (§7)
4. **`GET /api/players/:userToken` is unreachable** — shadowed by `GET /api/players/:sessionId`, registered first. (§6, §8.4)
5. **`getIdFromTokenBusiness` drops its return value** (missing `return` on the repository call) — independent of bug 4, so `data` would be `undefined` even if the route were reachable. (§8.4)
6. **`swapStatesRepository` doesn't validate row existence** before dereferencing `.state`, unlike `kickPlayerRepository`. (§8.8)
7. **Share links are hardcoded to `http://localhost:5173`** in `sessionBusiness.ts`/`playerBusiness.ts` — not environment-configurable, will produce wrong links in any non-local deployment.
8. **Frontend `SwapToWaitlistPopup` swap is local-state-only** — doesn't call the backend's `swapStates` endpoint, so the swap doesn't persist. (§11)
9. **`PlayerPage`'s "who am I" lookup is broken** as a consequence of bug 4. (§11)
10. Player-count/promotion logic in `deletePlayerRepository`/`kickPlayerRepository` is **capacity-driven, not per-player-state-driven** — correct for tested flows, but worth understanding precisely rather than assuming. (§8.5, §8.7)
